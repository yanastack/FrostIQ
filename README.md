# FrostIQ — Arduino UNO Q cold-storage anomaly prototype

FrostIQ is an **offline, on-device investigation and decision-support prototype** for cold-storage operations. It combines readings from a **Modulino Thermo** and **Modulino Distance** sensor with door-state tracking, an on-board decision-tree classifier, a board-hosted dashboard, and an illustrative response-comparison panel. It is not a certified refrigeration or food-safety monitoring system.

## Implemented / real prototype components

- **Real sensor acquisition:** The included `FrostIQ_Sensors/FrostIQ_Sensors.ino` reads the Thermo and Distance sensors; `board_feed.py` forwards the board-local Arduino router readings to `backend.py`. The motion sensor is unavailable in the supplied hardware setup; missing readings retain their error or unavailable status.
- **Adaptive door detection:** `door_status.py` learns a closed-position baseline from the first **15 valid distance samples while the door is held closed** and smooths subsequent readings over approximately four seconds. Physical calibration and live end-to-end operation still require verification on the target UNO Q.
- **On-device ML:** `train_on_uno_q.py` uses scikit-learn to fit a decision tree **on the UNO Q Linux processor**, using separate labeled recordings and whole-trial holdouts. `model_runtime.py` interprets the exported tree locally, enabling **live predictions when a trained model is present**. No training data or model weights are included in this public archive; a fresh deployment must train locally or use a board-local model generated by the team.
- **Operational dashboard:** `backend.py`, `dashboard.py`, and `monitor.html` display temperature history, door state, manually entered load arrivals, predictions or their availability status, and comparison of possible operational responses. All project processing, training, inference, and scenario calculations must run on the UNO Q; a laptop is only used for development and viewing the board-hosted page.

## Reported prototype evaluation

**Team-reported:** The decision-tree model was trained on **9 labeled trials**, with **whole trials held out** for evaluation, and scored **98.9% on a small held-out set**. This is a **prototype result, not a general accuracy claim**. The evaluation report and model weights are not in the supplied release ZIP, so the result is not independently reproducible from this repository alone. A tree prediction is **one possible explanation of a sensor pattern, not a diagnosis** of cooling-equipment failure or food safety.

## What is staged or simulated

- The cooling-failure scenario is **staged by warming the temperature sensor**; the prototype does not establish a real refrigeration failure.
- Temperature thresholds are **operator-configured assumptions**, not universal food-safety limits.
- Thermal exposure estimates, potential inventory impact, intervention delays, downtime, and response-cost comparisons are **illustrative proxies, not forecasts or product-safety determinations**.
- Sensor temperature represents the sensor environment, **not a product's internal temperature**.

## Optional: Multi-room what-if illustration (invented data)

The standalone [rooms simulator](ROOMS_SIM.md) demonstrates a **fictional** three-room loading schedule and rule-based response ideas. It does **not** read physical sensors, the FrostIQ database, the live model, or the main backend. It runs on its own web page on port 8010; it is **not evidence of multi-room deployment**. All room responses, per-item thresholds and estimated time above threshold are invented **room-air modeling assumptions**, not food-core temperature measurements, food-safety conclusions, or validated recommendations to relocate inventory or change equipment setpoints.

Run it **on the UNO Q** as a separate optional demo: `python3 rooms_sim.py --serve --port 8010`. Open `http://<UNO_Q_IP>:8010` from a laptop browser. The regular FrostIQ dashboard stays on port 8000.
